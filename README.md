## 踩坑记录
（记录调试过程中解决的问题）
1.SysTick_RVR的计数序列为什么减1
计数器从 RVR 的值开始，每一拍减 1，减到 0 那一拍也算——所以从 N 数到 0 一共是 N+1 拍。要 4000000 拍，RVR 就得写 3999999。记住"数到 0 算一拍"这半句，比"多算一次"更不容易忘，因为它直接对应硬件行为。
2.中断中关计数器 的后果
中断服务函数的职责是"响应事件"，不是"管理事件的来源"。 SysTick 的价值就是"硬件自己周期性地喊你"，如果你在中断里把计数器关了，等于喊你的人被你永久性解雇——LED 闪一次就永远停，而且这个 bug 极隐蔽：程序没死，主循环还在跑，就是灯再也不亮。正确分工：想让闪停，改主循环里的逻辑（比如加条件判断），让 handler 照旧每 500ms 来干活，干不干由主循环说了算。这个"handler 永远准点、决策权在主循环"的结构，就是以后 volatile 标志位模式的雏形。
3.中断后不清标志的后果
COUNTFLAG=1 是中断挂起（Pending）的证据，CPU 从中断返回时会检查："还有挂起的请求吗？"——标志还在，它立刻又跳进来。所以死循环的本质是"返回即重入"，主循环永远轮不到。顺带回答你上次那个疑问：开中断前读 CSR 清标志防的场景是——复位后计数器可能在空转，若恰好在使能前数到过 0，标志挂着 1，你一开 TICKINT，CPU 立刻"补发"一次中断，LED 第一次翻转的时机就乱了 500ms 以内的随机量。时序类 bug 的特征就是这样：功能大体对，边界悄悄错。
